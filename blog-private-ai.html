NOTE 05 · PRIVACY & CRYPTOGRAPHY · SIP-0005 5 min read

Auditable Private AI: Air-Gapped Local Mode and Blind-Relay E2EE

Most AI privacy tiers are policy promises hidden behind closed servers. In SIP-0005, we engineered fail-closed local air-gapping and coordinator-blind end-to-end encryption in plain, auditable client source.

ABSTRACT

We specify and implement two cryptographic and architectural privacy guarantees for Space AI tooling: (1) strict fail-closed loopback air-gapping (local-only) that refuses network egress with HTTP 503 if no local model is running, and (2) blind-relay end-to-end encryption (space-e2ee-v1) using worker-signed ephemeral X25519 keys and per-request HKDF-SHA256 / AES-256-GCM envelopes (<1 ms crypto overhead). We pair both with an explicit hardware threat model distinguishing coordinator-blind personal GPUs from attested Confidential Compute enclaves.

1. No silent downgrades: fail closed by default

A recurring failure mode in distributed AI tools is silent fallback: a user selects a private mode, the private backend happens to be busy, and the client quietly forwards plaintext code to a public cloud endpoint anyway.

Under SIP-0005, strict privacy modes (local-only, e2ee, hardened-docker, tee) always fail closed (HTTP 503 / 403) when eligible compute is unavailable. Downgrading requires explicit caller opt-in and echoes transparent audit headers (X-Space-Privacy-Applied, X-Space-Privacy-Downgraded) so silent leakage is structurally impossible.

2. How blind-relay E2EE (space-e2ee-v1) works

Suppose you own an RTX workstation or Mac Studio at home and want to use it remotely from a laptop or coding agent through api.spaceresearch.ai without our coordinator, CDN, or ISP ever reading your prompts or responses:

  • In-RAM forward-secret keypair: On startup, the worker generates an ephemeral X25519 keypair exclusively in memory and signs its public key with its persistent Ed25519 identity key.
  • Client-side anti-MITM verification: Before encrypting, the client locally re-verifies the worker's Ed25519 signature over the X25519 public key. When pinned to your own node identity, even a compromised relay cannot intercept or substitute the key exchange.
  • Per-request AES-256-GCM envelopes: Every prompt uses a fresh ephemeral client X25519 key, a random 96-bit nonce, and domain-separated HKDF-SHA256 keys for request and response payloads — adding under 1 millisecond of cryptographic overhead.
  • Hashed private team pools: With --private-pool, both client and worker hash the shared pool secret locally via SHA-256 so the secret itself never crosses the wire, and public traffic is excluded from private nodes.

3. An honest hardware threat model

Good security research states its exact boundaries plainly. Consumer GPUs (including GeForce RTX 30/40/50-series) and consumer CPUs do not support hardware-encrypted VRAM enclaves (NVIDIA Confidential Computing or AMD SEV-SNP).

4. Independently auditable source

Every line of the client proxy, air-gap filter, and space-e2ee-v1 cryptography ships in plain source with deterministic SHA-256 checksums and automated anti-MITM unit tests. Anyone can inspect the code and run space privacy-check --json locally without trusting hosted claims.
